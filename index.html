Field report — a live client engagement

The app went down during clinic hours. Forty-eight hours later it couldn't take the schedule with it.

The most useful thing I've built came out of the worst day of the project.

The system

A workload-based scheduling app for a pediatric therapy clinic, live in production since August 2026 and replacing a fully paper process.

~35,000 lines. 30 REST endpoints, 15 role-gated pages, zero frameworks and zero npm dependencies — PHP, SQLite, and a vanilla-JS progressive web app. 116 commits in 38 days, single author.

In daily use

573 audit rows in 18 days across 29 sessions, 14 in-app feedback notes from real staff, 16 nightly production backups, database growth 143 KB → 938 KB.

Underneath: an eight-component quarter-hour workload model with hard over-capacity blocking, a filter-and-rank substitute-therapist selector, and a conflict engine that behaves identically for saved and unsaved bookings.

The outage

Thirty minutes with the app unreachable, mid-day. Staff needed the day's schedule and had no second path to it. A scheduler that only exists on one host is a single point of failure for a working clinic.

The response

A zero-dependency Node service on a managed host, first commit to production in under 48 hours. It mails the schedule out on its own timer, so a host that is down no longer means a clinic that is blind.

Outbound only: no public IP, no inbound listener, nothing new to attack.

The constraints

Server-side data minimization — a whitelist projection, de-identified case codes, and clinical progress notes that never leave the host.

Hand-rolled SMTP client and spreadsheet writer, because the dependency budget was zero. 157 tests, including both 2026 daylight-saving transitions.

Staying in sync

Reports render by executing the production app's own recurrence code inside a sandboxed VM, rather than reimplementing it. The spreadsheet cannot disagree with the screen.

First real end-to-end send delivered. Recipient rollout is still pointed at a test address.

What the audit found — and what I changed afterward

I commissioned a security audit of my own application before launch. It found two launch-blocking criticals: an unauthenticated install-takeover path, and a cross-role read exposure across 26 tables. Both were closed before go-live, alongside Argon2id hashing, email one-time codes, CSRF validation before body parsing, a full audit log, and strict CSP/HSTS.

Later, an unapproved CI push reached production. I removed auto-deploy entirely, revoked the CI credential, and moved to manually authorized releases with post-deploy health assertions. The interesting part of a process failure is what the process looks like after it.

The Librarian — retrieval over an entire machine

Running now

Grounded question-answering over everything on this workstation, served to AI coding agents as an 8-tool MCP server. Hybrid retrieval, graceful degradation, and an eval harness that can block a release.

PythonSQLite FTS5BM25 Dense vectorsRRFMCP CI evals
  • Corpus: 3,190 files, 14,534 code symbols, 18,094 768-dimension vectors, 19,229 full-text documents.
  • Hybrid retrieval: Okapi BM25 (k1=1.2, b=0.75) and a dense cosine arm fused by reciprocal rank fusion (k=60), then a custom rerank stage over heading-chunked prose.
  • Content-hash incremental embedding: 21.8× batch speedup, 324 ms → 14.9 ms per text. Degrades cleanly to full-text-only when the embedding arm is unavailable.
  • 613 live queries in 30 days, 67% machine-to-machine. Five-provider fallback chain; ~92% of answers served by the cheap primary.
  • CI-gated eval harness: 22 graded questions, release blocked under 90%, and the deterministic subset must pass with every LLM provider down. Accuracy went 86.4% → 100%.
  • Admission control: a two-slot capacity line that returns {busy, position, ETA} instead of queueing silently.

Credit — the BM25 and RRF constants were harvested from an Apache-2.0 project and are credited in the source. The integration, overlap gate, salience scoring, sensitivity filter, and cache fix are mine.

Incident desk — a deflection ladder

Running now

A self-healing monitor over 15 production backends on a 15-second probe loop. The architecture is a cost ladder: cheap things try first, and a model is the last resort before a human.

  • 53 days: 612 incidents, 72.9% auto-resolved, mean time to resolution 55 seconds, 0.33% escalated to a human.
  • 419,000 health probes retained (~60K/day) with per-service 24-hour uptime objectives.
  • Tier 1: scripted restart playbooks, 75.6% first-line success. Tier 2: LLM triage — only 3.3% of tickets ever reach a paid model. Tier 3: a person. Triage diagnoses and never executes.
  • Safety rails: a config validator that rejects catch-all kill patterns, a four-restart-per-hour circuit breaker, and an independent kill-witness auditor. 7 MCP tools, 30 routes, 75 tests.

Scope — these are infrastructure incidents, not customer support tickets. The transferable part is the deflection architecture, not the domain.

LLM cost governance

FinOps

A USD-exact per-call ledger, built because I could not answer "what is this feature costing me?" from any vendor dashboard. Then a control plane on top of it.

  • Ledger: 2,129 calls over 61 days, 21 models, 8 providers, 38 use-case surfaces, 41M tokens, 64% input-cache hit rate. 100% of rows carry both surface and cost.
  • Routing outcome: cost per call −71% (from $0.048 to $0.014) while volume grew +51%; premium-provider share fell 52% → 19%.
  • Self-hosted control plane on PostgreSQL 17 with per-use-case virtual keys and hard 30-day budgets — built because the provider offers no per-key limits.
  • Build vs. buy: I audited a hosted tracing product and rejected it — roughly 40 call paths bypass any proxy, so the in-process ledger has coverage a gateway structurally cannot reach.
  • Degradation path: a raw-socket TCP probe (milliseconds, versus ~2s of retries on Windows) resolves gateway / direct / none. 852 calls flowed uninterrupted through fallback.

Scope — the −71% is a routing-policy outcome over time, not a controlled A/B. The proxy itself fronts two models from one provider; the eight-provider breadth lives in the ledger.

Agent platform — 122 tools, three-layer authorization

Daily driver

The desktop platform the rest of this page runs inside: 678 HTTP endpoints, 202K lines of Python and 74K of Svelte, 2,948 test functions, 6 self-built MCP servers, 19 local services. Roughly three months of work.

  • 122 agent tools (counted two independent ways) across filesystem, shell, calendar, health and messaging, on a vendor-neutral protocol that runs the same loop against local and hosted models.
  • Authorization in three layers: a positive per-surface allowlist that fails closed, an engine-conditional denylist enforced at five chokepoints, and a credential-aware filesystem perimeter. 32 dedicated gate tests.
  • Five-zone token-budgeted prompt (32k context) with a byte-identical static prefix so caching actually hits, protected by golden-file regression tests.
  • 5.3× prompt reduction for small-model surfaces — 7.4k to 1.4k tokens — via a curated catalog plus a scored tool-search escape hatch.
  • Manager orchestrator with a hierarchical delegate matrix and a budget governor; illegal plans are repaired rather than executed.

Scope — the orchestrator is designed and validated across 6 runs and 17 delegation events. It has not been run at scale.

Local dual-GPU infrastructure

One RTX 2080 (8 GB, CUDA) and one RX 9060 XT (16 GB, ROCm) with 64 GB of RAM, shared by a dozen processes that all want the whole card.

Things I got wrong

What broke, and what I changed after.

I measure what I build, so the numbers sometimes come back against me. When that happens I write it down and change the design.

0.0 I had been repeating a "90% context savings" figure for the retrieval layer. My own instrumentation measured zero. The instrumentation stayed; the claim did not.
6 defects Found only by live-firing real services — and every one of them had green tests beforehand. Including a cache with a 0% hit rate, because its 2.0-second TTL sat under a 2.5-second poll. It read as correct in review. This is where my anti-drift test doctrine came from.
3.3%, not 100% The incident desk's headline gets misread as "a model triaged 612 tickets." Only 21 of them ever reached a model. The cheap ladder catching the other 591 is the actual win, and inflating it would hide the design.
4 features Type-clean, tested, and completely inert — nothing in production ever called them. That produced the rule I now apply before building anything: name the production caller first, or it isn't built.
Not built Hosted LLM tracing. I audited it, found ~40 call paths that bypass any proxy, and deliberately did not adopt it. The rejection is the result, and it's more useful than the integration would have been.
Gate failed I pre-registered an adoption threshold for the 744B local model before running it, missed the threshold, and changed the design instead of moving the goalpost.
6 runs The manager orchestrator is validated, not proven. Six runs and seventeen delegation events is a demo with evidence, not production scale — it stays described that way until it earns otherwise.
How I work

Four rules, each one earned by a defect that shipped.

Every one of them came out of something that passed review, passed tests, and was still wrong.

Verify the effect, never the command

An exit code of 0 proves nothing. Assert the observable end state instead: exactly one listener after the restart, the live payload actually carrying the new value, the pattern that both compiles and matches a real process. A kill command once reported success while matching nothing at all.

Name the production caller first

What calls this, in production, after the change lands? If there's no answer, the work is decoration. A thing with no caller is not built, however green its tests are.

Field names are part of the contract

A flag called execution_enabled meant "the code switch is on" and got read as "this app is armed to act." The name is what let the mistake hide for weeks. Names that can't be misread cost nothing extra to type.

Derived state is answered by the code that acts

"Is this armed?" was answered in five places once, and a dashboard confidently said no while the executor said yes. One function, everyone reads it. Cross-service tests run against real payloads or goldens captured from them — never hand-written fakes, which agree with you forever.
